# User Preferences
- Use graphify for codebase exploration every time it is available and up to date — check version/freshness first (e.g. manifest, `GRAPH_REPORT.md`, dist from HEAD) and fall back to direct source reading only when its artifacts are stale. Confidence: 0.85
- Enter plan mode and write a structured plan before implementing. Confidence: 0.8
- Prefer minimal, surgical changes — fix what's broken, don't over-engineer or add unnecessary files. Confidence: 0.9
- Follow existing codebase patterns rather than introducing new ones. Confidence: 0.9
- Run tests and type checks after changes to verify correctness. Confidence: 0.8
- Update graphify after making code changes. Confidence: 0.8
- Explicitly document scope: what's included and what's skipped. Confidence: 0.8
- Distinguish pre-existing failures from new regressions. Confidence: 0.8
- Prefers concise, direct answers to status questions (e.g., "Is our page ready?" → short confirmation + how to verify). Confidence: 0.7
- Likes honest risk reporting — call out untested areas or low-risk assumptions. Confidence: 0.7
- Backend: Laravel with Domain-Driven Design structure (`app/Domains/{Domain}/Services/`). Confidence: 0.9
- Frontend: React + TypeScript with Inertia.js. Confidence: 0.9
- Report pages use shared components: ReportLayout, ReportToolbar, DateFilter, SummaryCards, ReportRow. Confidence: 0.9
- Report routes should use controller methods, not closures. Confidence: 0.9
- Expects features to be fully wired through all UI layers — sidebar navigation, mobile nav, and landing pages — not just the page itself. Confidence: 0.8
- Reports should include bill-wise / per-transaction detail lists alongside summary cards — not just aggregated totals. Confidence: 0.8
- When redesigning report features, proactively investigate data anomalies (e.g. inflated losses) before implementing UI changes. Confidence: 0.7
- Expects new report list views to reuse existing shared table components (e.g. ReportTable) rather than building from scratch. Confidence: 0.9
- Audit reports and analysis deliverables should be written for a non-technical audience — explain flaws and business impact in plain language, not just technical terms. Confidence: 0.8
- Long analysis/review deliverables should be delivered as a written file rather than dumped inline in the chat — and the file belongs inside the project's own `docs/` folder, not an external plans directory (corrected the agent when it wrote to `~/.commandcode/plans/`). Confidence: 0.7
- Validate calculations against real data (e.g. import SQL dumps, run queries) before trusting reported numbers — when a seed/dump file exists (`.commandcode/*.sql`), import it into a scratch database and actually run the code/queries against it instead of declaring production access unavailable and shipping assumptions. Confidence: 0.8
- For frontend/UI work, explicitly wants the specialized react and UI/UX skills applied (e.g. ui-ux-pro-max, frontend-design) alongside graphify navigation. Confidence: 0.7
- Designs and evaluates UI feedback for non-technical end users, not developers — avoids ambiguous or contradictory messages (e.g. a "deleted" toast when nothing was deleted); blocked/error states should explain why in plain language and offer a clear next step rather than a dead end. Confidence: 0.75
- Expects hidden/archived/deleted entities to be excluded consistently from every listing, picker, and report surface so their state is never ambiguous — e.g. an archived product must not still appear available in inventory, sales, or purchase screens. Confidence: 0.7
- Prefers one consistent, simple rule over nuanced per-context exceptions (e.g. chose to exclude archived products from all money numbers, valuation, and reports rather than keep them in valuation while dropping them only from alerts). Confidence: 0.6
- Expects loading/pending states to be visibly obvious (top progress bar, spinner, skeleton, animation) — an indicator that is technically present but invisible does not count as feedback. Confidence: 0.7
- Delegates judgment calls to the agent — prefers it to decide and proceed autonomously on fixes it deems important (e.g. "Proceed with the fix if important") rather than stopping to ask for sign-off on every issue; when offered optional side tasks (e.g. resetting a test password) mid-plan, expects a "no not now" and continued progress on the main work. Confidence: 0.8
- Treats a stable, working project state as an explicit frozen base — wants it marked (e.g. an annotated `base-v1.0` tag) before starting variant work, so the base version is never disturbed. Confidence: 0.7
- Prefers product variations to live in the same repository as long-lived branches checked out side by side via `git worktree`, rather than a separate clone/fork or constant branch switching. Confidence: 0.7
- Shared capabilities belong in the base first and get merged into variations; only variation-specific work stays on the variation branch. Confidence: 0.65
- Before implementing a significant plan, wants an explicit review gate that challenges the plan rather than validating it — verify assumptions against the real code paths (don't trust field names or the plan's own claims), surface contradictions and risks, and wait for explicit approval before writing any code. Confidence: 0.7
- Long analysis/assessment deliverables must be evidence-graded: label every claim as confirmed (verified in code/schema/DB) vs inferred vs recommendation vs unknown business decision, and never fabricate measurements — if live data is unavailable, say so explicitly and list the exact queries/checks that would establish it. Confidence: 0.65
- Documentation (ADRs, READMEs, architecture docs) is not evidence: verify every claimed capability against actual source code, schema, and live database state, and explicitly call out where docs and reality diverge ("do not claim something exists unless verified in source code"). Confidence: 0.7
- Schema/data migrations must be additive and compatibility-first: never delete or rewrite historical business records (sale/purchase totals, quantities, IDs, invoice/payment references), never silently recompute balances or stock, and never fabricate historical accuracy from today's costs — ambiguous or unrecoverable data is flagged and reported for a business decision, not guessed or auto-corrected. Confidence: 0.8
- When reporting a data problem, hand over the drill-down evidence so he can verify it himself — name the exact records (e.g. invoice numbers) behind any claim, and never declare his own data "wrong" (implausible cost, bad input) until the units/semantics are confirmed against the real records; he will pull up the product/detail screen to check and pushes back hard on unverifiable assertions. Confidence: 0.75
- Keeps a single clean database as the source of truth for local/dev work — after a scratch import or comparison, expects the leftover side databases (baseline/compare copies, old snapshots) to be dropped rather than accumulated side by side. Confidence: 0.55
- Expects printed output (invoices, reports) to be a complete, real document — all pages and all rows print (not clipped to the first viewport), table headers repeat per page, and each document has a proper header/footer template; a missing or ugly print template counts as a defect, not a nice-to-have. Confidence: 0.7
- Print/PDF output must be a purpose-built, branded document template (business identity, typography, real document layout) — not a print of the live app screen, which he calls "screenshoting the pages"; this includes PDF downloads, which should come from dedicated server-rendered document templates rather than a browser "Save as PDF" of the React page, and correct pagination alone is not "fixed" if the template is unbranded. Confidence: 0.7
- Expects mobile to be a first-class experience — wants a genuinely mobile-friendly, good-looking interface where print, share and other actions are actually usable on a phone (sticky/bottom action bars, real tap targets, no desktop-only layouts), not a squeezed-down desktop view. Confidence: 0.7
- Print/PDF documents must be light-themed (explicit white page background, dark ink — never leaving background/theme to the viewer or inherited dark styling) and laid out compactly: he flags excessive padding/margins/whitespace as a defect, so keep page margins and section spacing tight rather than airy. The app's dark theme must not leak into reports/PDF at all — dark-on-dark elements there are reported as a bug even though light mode "is fine". Confidence: 0.8
- Data lists must never silently truncate: if a table/list is limited to a page size, it needs visible pagination (page X of Y, prev/next) so every record is reachable — he reports "shows only 25 and there is no pagination" as a defect. Confidence: 0.75
- Printed documents (report headers/footers, invoice PDFs) must be fed by the real settings module — the shared server-side business settings (name, address, phone, email, website) — not mock/hardcoded placeholder data; he treats a report using mock settings as a bug to correct. Confidence: 0.6
- Wants "screen options" (a visible rows-per-page selector, e.g. 25/50/100/200, wired through to the server) on every paginated listing so more records can be shown than the default 25 — and applied "wherever required" across lists, not just the one screen he named; fixed presets are not enough, he wants a "Custom…" escape hatch (numeric input + Apply, server-side clamped) so he can pick any count to see more or fewer records. Confidence: 0.75
- Listing screens should conserve vertical space: filter panels collapsed by default behind a Filters toggle (search stays visible), because a permanently expanded filter row "takes too much space". Confidence: 0.65
- Search boxes must be forgiving and broad, not strict: match partial/loosely formatted input (case, dashes and spaces ignored in invoice numbers), span many fields — name, status, source, date, and numeric amounts (subtotal, discount, total, paid, outstanding) — and query the whole dataset server-side rather than filtering only the loaded page; "too strict or not working" and matches on later pages missing is reported as a defect. Confidence: 0.65
- Deployment target is cPanel with no Node — so built frontend assets (`public/build`) are committed on purpose, and asset merge conflicts are resolved by deleting and rebuilding (`rm -rf public/build && npm run build`), never by hand-merging chunks. Confidence: 0.7
