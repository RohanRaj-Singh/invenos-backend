# Product Unit Architecture — Final Implementation Plan

**Date:** 2026-07-28
**Status:** Final architecture review before implementation
**Principle:** Evolve the UX. Preserve the backend. One list of units.

---

## Executive Summary

After seven architecture reviews, the design is stable. This document captures the final decisions and the implementation plan.

### Core Decisions

| Decision | Verdict |
|----------|---------|
| **Default Unit** | The user's chosen inventory unit + default transaction pre-select. NOT smallest/root/inferred. |
| **Purchase vs Sale units** | **Unified** — one list of "all supported units." The transaction determines which is used. |
| **Relationship Editor** | Primary authoring UX. Flat, bidirectional, natural language. |
| **Backend runtime** | **Preserved.** `selling_units` + `product_packaging` remain. Transformation layer bridges UX to backend. |
| **Database changes** | **Minimal.** No new tables. Migration not required for existing products. |
| **Derivation Engine** | **Preserved.** Processes `product_packaging` generated by the transformer. |

### What Changes vs What Stays

```
NEW:                     PRESERVED:
  UnitRelationEditor       ProductService
  Transformer function     PackagingDerivationEngine
  (flat → backend format)  SaleService
                           PurchaseService
REMOVED:                   InventoryService
  Inline conversion        SaleBill.tsx
  Separate packaging       PurchaseBill.tsx
    + selling sizes UI     Clinic module
  "Base Unit" label        All reports
                           All printing
                           All barcode scanning
```

## 1. Default Unit — Refined Definition

### What It Is

The Default Unit has exactly two responsibilities:

```
DEFAULT UNIT
     │
     ├── 1. INVENTORY ANCHOR
     │       Stock is tracked in this unit.
     │       All conversions normalise through this unit.
     │       `products.base_unit_id` stores this.
     │
     └── 2. DEFAULT TRANSACTION UNIT
           Purchase Bill → pre-selects this unit
           Sale Bill → pre-selects this unit
           Opening Stock → uses this unit
           Stock Adjustment → uses this unit
           Clinic Visit → uses this unit
           User may freely change before saving.
```

### What It Is NOT

| NOT This | Why |
|----------|-----|
| Smallest unit | Business may count in Boxes, not Capsules |
| Physical unit | Business may count in Cartons (not a physical atom) |
| Packaging root | No hierarchy implied |
| Inferred by system | User chooses explicitly |

### UX

```
┌──────────────────────────────────────────────┐
│  I count inventory in: [Box ▾]               │
│                                              │
│  (Stock will be tracked in Boxes.            │
│   Sales and purchases will default to Box.)  │
│                                              │
│  What other units do you use?                │
│  1 [Strip ▾] = [10] [Capsule ▾]  Rs. 50     │
│  1 [Carton ▾] = [24] [Box ▾]    Rs. 4,500   │
│  [+ Add unit]                                │
└──────────────────────────────────────────────┘
```

## 2. Unified Units — No Purchase/Sale Separation

### Principle

> The product defines all supported units. The transaction determines which is used.

A product has ONE list of units:

```
Available Units for Amoxil 250mg:
  Capsule  → qty: 1,  price: Rs. 5
  Strip    → qty: 10, price: Rs. 50
  Box      → qty: 120,price: Rs. 500
  Carton   → qty: 1200,cost: Rs. 4,500
```

**Purchase Bill:** User picks "Carton" → cost column pre-fills Rs. 4,500
**Sale Bill:** User picks "Strip" → price column pre-fills Rs. 50
**Stock Adjustment:** User picks "Box" → adjustment in Box units

### Per-Unit Price/Cost Columns

| Field | NULL Means |
|-------|-----------|
| `sale_price = NULL` | This unit is not sold at POS (purchase-only unit) |
| `purchase_cost = NULL` | This unit is not purchased (sale-only unit) |
| `sale_price = 500, purchase_cost = 4200` | Both — unit is both sold and purchased |

### Edge Cases

| Scenario | How It Works | Implement Now? |
|----------|-------------|----------------|
| **Purchase-only unit** (Pallet) | `sale_price = NULL, purchase_cost = 24000` — Pallet shows in Purchase dropdown, hidden in POS | ✅ Yes — just omit from POS query |
| **Sale-only unit** (Sample) | `sale_price = 10, purchase_cost = NULL` — Sample shows in POS, hidden in Purchase | ✅ Yes |
| **Same unit, different prices** (Box retails Rs. 500, Box wholesales Rs. 4200) | Add TWO relationship rows: "Box (retail)" and "Box (wholesale)" with different names | ✅ Yes — name disambiguates |
| **Unit used for reference only** (Pallet = 24 Cases, no price) | Both `sale_price = NULL, purchase_cost = NULL` — Pallet exists for conversion math, not for transacting | ✅ Yes — valid use case |

**Verdict:** Unified list works. Purchase-only and sale-only units are handled by NULL price columns. Implement now.

## 3. Relationship Editor — Final UX

### Default State (Simple Product)

```
┌──────────────────────────────────────────────┐
│  Name: [Wheat Bread                        ] │
│  Count in: [Loaf ▾]                         │
│  Price: [Rs. 120 per Loaf]                  │
│                                              │
│  [Save]  ← one click, product complete      │
└──────────────────────────────────────────────┘
```

### With Additional Units

```
┌──────────────────────────────────────────────┐
│  Name: [Amoxil 250mg                       ] │
│  Count in: [Capsule ▾]                      │
│  Price: [Rs. 5 per Capsule]                 │
│                                              │
│  ── Other units ──                          │
│                                              │
│  +── 1 [Strip ▾]  =  [10] [Capsule]  ─────+ │
│  │  Sale price: [Rs. 50 per Strip]         │ │
│  │  Barcode: [____________]                │ │
│  +──────────────────────────────────────────+ │
│                                              │
│  +── 1 [Box ▾]  =  [120] [Capsule]  ───────+ │
│  │  Sale price: [Rs. 500 per Box]           │ │
│  +──────────────────────────────────────────+ │
│                                              │
│  +── 1 [Carton ▾]  =  [1200] [Capsule]  ───+ │
│  │  Purchase cost: [Rs. 4,500 per Carton]   │ │
│  +──────────────────────────────────────────+ │
│                                              │
│  [+ Add unit]                                │
│                                              │
│  [Save]                                      │
└──────────────────────────────────────────────┘
```

### UX Rules

| Rule | Implementation |
|------|---------------|
| **Defaults to natural direction** | User types "1 Box = 12 Strips" — stored as-is. If they type "12 Strips = 1 Box", normalise to "1 Box = 12 Strips" on save. |
| **Auto-compute the blank side** | If user types "1 Box = 12" and selects "Strips" — auto-compute right side. If they type "= 12 Strips" — auto-compute left side as 1. |
| **Prevent circular relationships** | On save: walk the graph. If Box → Strip → Box detected, reject with message: "Box and Strip already reference each other." |
| **Prevent duplicates** | If "Box = 12 Strips" exists and user adds "Box = 24 Strips" — warn: "Box already defined. Do you want to replace or add as a different name?" |
| **Auto-suggest units** | Type "k" → suggest "kg", "Kilogram (kg)", "Kilogram". Type "ca" → suggest "Capsule", "Carton", "Can". |
| **Normalise unit names** | "strip", "Strip", "STrips" → all resolve to "Strip" via existing `product_units` registry. |

## 4. Runtime Architecture (Preserved)

```
                           RELATIONSHIP EDITOR
                           (User-facing authoring UX)
                                  │
                                  ▼
                      TRANSFORMATION LAYER
                      (Pure function: relationships → backend format)
                          │                │
                          ▼                ▼
              ┌────────────────┐  ┌────────────────┐
              │ product_packaging│ │ selling_units   │
              │ (container→     │  │ (materialised)  │
              │  contains pairs) │  │                 │
              └───────┬─────────┘  └────────┬────────┘
                      │                     │
                      ▼                     ▼
         ┌────────────────────┐  ┌──────────────────────┐
         │ Derivation Engine  │  │ Purchase Service     │
         │ (graph walk →      │  │ Sale Service         │
         │  verify consistency)│  │ Inventory Service    │
         └────────────────────┘  │ Clinic Service       │
                                 │ Reports              │
                                 │ POS                  │
                                 └──────────────────────┘
```

### What Each Layer Does

| Layer | Responsibility | Status |
|-------|---------------|--------|
| **Relationship Editor** | User defines units and their relationships. No backend concepts exposed. | **New** |
| **Transformation Layer** | Converts flat relationships to `product_packaging` + `selling_units`. Pure function, ~80 lines. | **New** |
| **`product_packaging` table** | Stores container→contains pairs for derivation engine. | **Preserved** |
| **Derivation Engine** | Walks packaging graph, computes transitive quantities, verifies consistency. | **Preserved** |
| **`selling_units` table** | Materialised runtime model. Read by all transaction flows. | **Preserved** |
| **Sale, Purchase, Inventory, Clinic, Reports, POS** | All read `selling_units`. All unchanged. | **Preserved** |

### Why This Architecture

| Concern | Answer |
|---------|--------|
| **Why not replace `selling_units`?** | Too many integrations depend on it. No runtime benefit to replacing it. |
| **Why keep the derivation engine?** | It already validates and materialises the graph. Correct one-way flow. |
| **Why a transformation layer?** | It's the only way to add a new UX without changing the backend. |
| **Why not store relationships directly?** | Because the runtime needs materialised units (with prices, barcodes, defaults). Derivation produces these. |

## 6. Inventory Model

### How Inventory Works

```php
// Stock is always tracked in the Default Unit
$product->stock_quantity; // 1250 (in default units)
$product->default_unit_id; // 'capsule'

// When a Sale deducts 2 Boxes:
$relationship = $product->relationships->where('unit_name', 'Box')->first();
$defaultQty = 2 * $relationship->quantity; // 2 × 120 = 240
$product->stock_quantity -= $defaultQty; // 1250 - 240 = 1010
// Stock is now 1010 Capsules
```

### What Does NOT Change

| Operation | Current | After |
|-----------|---------|-------|
| **Stock addition** | `qty × relationship.quantity` | Same |
| **Stock deduction** | `qty × relationship.quantity` | Same |
| **Stock count** | Physical count in any unit → convert to default | Same |
| **Running balance** | In default units | Same |
| **Low stock alert** | Compared against default unit threshold | Same |

### What Changes

| Operation | Current | After |
|-----------|---------|-------|
| **Where relationship is read from** | `selling_units.quantity` | `selling_units.quantity` (same table, same column) |

**No inventory model changes.**

## 7. Purchase & Sale Integration

### How Purchase Bill Uses Units

```
Product: Amoxil 250mg
Available units: Capsule, Strip, Box, Carton

Purchase Bill:
  Supplier: Al-Rashid Pharma
  Items:
    Amoxil 250mg × [1] [Carton ▾] @ Rs. 4,500
                                          ↑
                          Dropdown shows all units
                          Default pre-selects the Default Unit
                          User selects Carton
                          Cost per Carton: Rs. 4,500 (from relationship)
```

### How Sale Bill Uses Units

```
Product: Amoxil 250mg
Available units: Capsule, Strip, Box, Carton

Sale Bill:
  Customer: Walk-in Customer
  Items:
    Amoxil 250mg × [2] [Strip ▾] @ Rs. 50
                                        ↑
                        Dropdown shows all units
                        Default pre-selects the Default Unit
                        User selects Strip
                        Price per Strip: Rs. 50 (from relationship)
```

### Key Insight

Both Purchase and Sale read the **same list of units** from `selling_units`. The list is identical. The transaction context (purchase vs sale) determines which price column is used and which UI shows.

### Changes Required

| File | Change | Lines |
|------|--------|-------|
| `SaleBill.tsx` | None — already reads `selling_units` | 0 |
| `PurchaseBill.tsx` | None — already reads product data | 0 |
| POS unit dropdown | None — already displays `selling_units` | 0 |

**Zero changes to Purchase and Sale flows.**

## 10. Migration Strategy

### Existing Products (No Migration Required)

| Product State | What Happens |
|--------------|-------------|
| **Created with old form, never edited** | Existing `selling_units` + `product_packaging` continue working unchanged |
| **Created with old form, edited with new UI** | Transformer overwrites old data with new format on save |
| **Created with new UI** | Transformer generates `product_packaging` + `selling_units` — same format as old products |

### Old Product Edited With New UI

```
Before edit:
  selling_units: [Capsule(qty=1), Strip(qty=10), Box(qty=120)]
  product_packaging: [Box→12→Strip, Strip→10→Capsule]

User opens edit form:
  → Transformer reads existing selling_units + product_packaging
  → Converts back to relationship format for display
  → User edits relationships
  → On save, transformer generates new selling_units + product_packaging
  → Old rows are deleted and replaced
```

### Rollback

If the transformer produces incorrect data:

```bash
# Revert the product to its state before the edit
git checkout HEAD~1 -- app/Domains/Products/Services/ProductService.php
# Run a database restore from backup
```

Since the transformer only affects one product at a time (on edit), a rollback is per-product, not system-wide.

## 11. Risks & Edge Cases

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| **Circular relationships** | Low | Validator detects cycles on save, rejects with clear message |
| **Duplicate unit names** | Low | Autocomplete + normalisation prevents "Strips" vs "Strip" |
| **Transitive inconsistency** | Medium | Each relationship stored independently. Transformer validates on save. User prompted to fix. |
| **Transformer bug corrupts data** | Low | Old data is replaced only on save. Revert is per-product. |
| **POS shows wrong default unit** | Low | `is_default_sale` flag on the default unit's selling_unit row |
| **Purchase shows units without purchase_cost** | Low | Filter `selling_units` to those with `purchase_cost IS NOT NULL` in Purchase Bill |
