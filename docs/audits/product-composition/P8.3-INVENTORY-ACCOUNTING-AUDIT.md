**Date:** 2026-11-15
**Branch:** `feature/product-composition`
**HEAD:** `50be1bd911f8c0ad46a9232aac4396837f457843` (no commit)
**Result:** Source-branch composition/manufacturing inventory and costing integrity verified, with two corrected high-severity accounting gaps and documented limitations.

---

## 1. Inventory authority

The canonical stock authority on this branch is:

- `products.stock_quantity` — current base-unit balance;
- `inventory_transactions` — signed ledger with `running_balance`;
- `products.uncosted_qty` — quantity of stock with no reliable cost;
- `products.average_cost` — weighted-average cost for costed stock.

All composition-related stock movement goes through `InventoryService`:

| Operation | Method | Ledger type | Direction |
|---|---|---|---|
| Component consumption | `recordConsumption` | `consumption` | Negative |
| POS parent sale (simple/assembly) | `recordSale` | `sale` | Negative |
| Returned parent stock | `recordReturn` | `sale-return` | Positive |
| Recovered component stock | `recordReturn` | `sale-return` | Positive |
| Production receipt | `recordProduction` | `production` | Positive |
| Production reversal | `recordProduction` | `production` | Negative |
| Manual adjustment | `recordAdjustment` | `adjustment` / `damage` | Signed |

No composition or production service writes `products.stock_quantity` directly. `ProductionService` writes `average_cost` and `uncosted_qty`; stock itself is written by `InventoryService`.

## 2. Composition execution

Verified in `CompositionExecutionService`:

- active consumption composition only (or assembly when required by production);
- nested consumption expansion with depth 20 and cycle defense;
- base-unit conversion through `ProductUnitService`;
- output scaling, wastage and absolute overrides;
- optional components omitted by default and validated server-side;
- repeated components aggregated into one ledger movement and one run item;
- all product rows locked in ascending id order;
- top-level composition version rechecked under lock;
- all mandatory component balances checked before any movement;
- component shortage rolls back the entire run;
- one canonical `consumption` movement per aggregated component;
- immutable run and run-item snapshots;
- cost snapshot uses `CostResolver`; unavailable cost is `null`, never zero;
- unique idempotency key claimed by the pending run before preflight.

**Result: PASS.**

Known narrow limitation: nested composition versions are not locked/revalidated after explosion. The top-level version is rechecked; a nested template change in the small window between explosion and movement is documented in P8.1.

## 3. POS integration

Verified in `SaleService`:

- one sale row and one commercial sale item per cart line;
- consumption products do not move parent stock;
- components never become sale items and never generate revenue;
- component consumption is executed after all commercial lines exist, inside the sale transaction;
- cumulative shared-component validation across multiple lines;
- `bypass_stock_check` does not bypass composition preflight;
- sale retry does not repeat consumption;
- composition cost is rolled from run items, not from the current product cost;
- sale deletion remains blocked while composition runs/returns exist.

**Result: PASS.**

P8 correction: simple/assembly products that consume uncosted stock now write `cost_complete = false` and a known-cost subtotal instead of silently valuing the uncosted portion at the previous average.

## 4. Costing

### Composition lines

- `CogsCalculator` reads `composition_run_items` for completed sale-linked runs.
- Multiple runs for one sale item are summed, not double-counted.
- Nested compositions are already flattened into final component run items.
- Partial/unavailable component costs retain the known subtotal and set `cost_complete = false`.
- `composition_cost_basis` is `none`, `exact`, `estimated`, `partial` or `unavailable`.

### Simple/assembly lines

- COGS remains `base_quantity * cost_price`.
- P8 adds `sale_items.cost_complete` and `sale_items.uncosted_quantity`.
- When a sale consumes uncosted stock:
  - known cost per base unit is stored for the costed portion;
  - the line is flagged incomplete;
  - COGS uses the known subtotal;
  - reports expose `simple_cost_complete`, `uncosted_simple_items`, `uncosted_simple_lines`.
- A line with no known cost stores `cost_price = null` and remains incomplete.
- Pre-existing simple-product behavior with historical null cost is otherwise unchanged.

### Report consistency

`SalesReportService`, `FinancialReportService`, `DayBookReportService`, bill-wise profit and the dashboard all use `CogsCalculator`. P&L, financial overview and balance sheet show generic incomplete-cost warnings covering both composition and stock lines.

**Result: PASS.**

## 5. Returns and material restoration

Verified in `ReturnService` + `CompositionReturnRecoveryService`:

- commercial refund/credit and material restoration are separate facts;
- composition sale lines never restock the commercial parent;
- restoration is explicit, not automatic;
- recoverable basis is `min(template_quantity, actual_quantity)`, excluding wastage;
- eligibility is cumulative and proportional across returns;
- over-declaration is rejected at creation and completion;
- restoration uses canonical `sale-return` movements;
- restoration is idempotent through unique `(return_item_id, composition_run_item_id)`;
- return reversal compensates restoration movements and refunds;
- run snapshots remain completed and immutable;
- COGS reversal uses the canonical cost calculator and does not double reverse;
- a sale with a return cannot be deleted.

Known limitation: restoration uses the run-item historical cost and does not update the component's weighted average. This is a P6 accounting policy choice, documented and unchanged in P8.

**Result: PASS with documented policy limitation.**

## 6. Manufacturing

Verified in `ProductionService`:

- draft creation/update/start/cancel are inventory-neutral;
- execution requires an active assembly composition belonging to the finished product;
- execution calls P3 with caller-owned transaction;
- components are consumed through P3;
- finished goods are received through the canonical `production` ledger type;
- production creates no revenue, sale, payment, receivable/payable or invoice;
- complete cost updates finished-goods weighted average;
- incomplete cost quarantines quantity in `uncosted_qty` and leaves `average_cost` unchanged;
- production history is immutable;
- reversal removes finished stock through a negative `production` movement;
- reversal does not restore components;
- reversal is blocked when finished stock is below the produced quantity;
- reversal is idempotent by unique key.

### P8 correction — reversal valuation

Before P8, reversal removed stock at the original production cost but left `average_cost` untouched. This overvalued remaining stock after later receipts changed the average. P8 now:

1. captures the finished product's stock, uncosted quantity and average before reversal;
2. writes the negative production movement;
3. refreshes the locked product so stale attributes cannot overwrite the new stock balance;
4. removes the original production cost from book value;
5. recalculates the average over the remaining costed quantity;
6. clamps uncosted quantity to the remaining stock.

Covered by `test_reversal_rebases_weighted_average_to_remaining_stock_cost`.

**Result: PASS after correction.**

## 7. Negative-stock and bypass review

- Composition preflight is stricter than the legacy `allow_negative_stock` setting; component shortages never execute.
- `InventoryService::applyMovement` still permits negative stock according to product/global settings for non-composition operations.
- Production reversal uses a `REV-` reference; stock was prechecked, so it does not rely on the bypass.

- No direct stock update was found in composition/production code.

## 9. Double-counting review

- Component costs are not added to sale revenue or COGS twice.
- `composition_runs.total_cost` is not used for COGS; run items are.
- Finished-goods production cost is not also added as a purchase or expense.
- Production is not revenue.
- Reversal does not restore components, so component cost remains consumed once.
- Return restoration does not create a second COGS reversal.
- Nested compositions are flattened to final components, so each consumed component is counted once.
- Production output is not double-valued: stock increases once and average cost is updated once.

## 10. Remaining limitations

| Limitation | Impact | Status |
|---|---|---|
| No warehouse/location ledger | Location is a snapshot; no per-location stock | Documented |
| Production reversal is quantity-based | Cannot identify a specific production batch after commingling | Documented |
| No component restoration on production reversal | Physical scrap/recovery needs a separate explicit workflow | Documented |
| Incomplete production stock | Flagged on sale; known-cost subtotal used, never fabricated zero | Corrected in P8 |
| Return restoration does not update weighted average | Historical cost restoration can drift average | P6 policy |
| Nested composition version race | Narrow concurrent template-change window | Documented |
| Reversed production summaries are gross | Rows expose status; no net summary field yet | Documented |
| Pre-existing inventory valuation page uses selling price | Not used by financial COGS | Out of scope |
| Two local reconciliation mismatches | Legacy fixture data | Not repaired |

## 11. Verdict

Composition execution, POS consumption, costing, returns, manufacturing and production reversal are internally consistent on the source branch. The high-severity uncosted-sale and reversal-average defects are corrected and covered by tests. No composition-related ledger mismatch was found.

The source branch is **production-ready with documented limitations**. The fashion branch requires separate company-stock and company-ownership integration before it can be declared ready.
