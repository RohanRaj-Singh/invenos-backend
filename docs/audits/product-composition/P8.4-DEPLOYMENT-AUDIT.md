## 2. Schema constraints

### Composition

- `product_compositions.product_id` → `products` RESTRICT;
- `product_composition_items.composition_id` → `product_compositions` CASCADE;
- `product_composition_items.component_product_id` → `products` RESTRICT;
- unique `(product_id, kind, version)`;
- unique `(composition_id, component_product_id)`;
- quantities/costs `decimal(14,6)`, wastage `decimal(6,3)`.

### Runs

- `composition_runs.composition_id` → RESTRICT;
- `composition_runs.product_id` → RESTRICT;
- `composition_runs.sale_item_id` → `sale_items` null-on-delete;
- unique `run_number` and nullable unique `idempotency_key`;
- indexes on `(source_type, source_id)` and `product_id`;
- run-item component → products RESTRICT; inventory transaction → RESTRICT;
- unique `(composition_run_id, component_product_id)`.

### Returns/recovery

- `return_component_recoveries.return_id`/`return_item_id` → CASCADE;
- composition run/run item/component/inventory movement → RESTRICT;
- unique `(return_item_id, composition_run_item_id)`;
- indexes on return, run and component;
- `returns.idempotency_key` unique.

### Production

- `production_orders.product_id`/`composition_id` → RESTRICT;
- `composition_run_id` nullable unique → RESTRICT;
- finished/reversal inventory transactions → RESTRICT;
- unique `production_number`, `idempotency_key`, `reversal_idempotency_key`;
- indexes on status, product, planned date and completed date;
- decimals `14,6`.

### P8 sale completeness

- `sale_items.cost_complete` boolean default `true`;
- `sale_items.uncosted_quantity` decimal `14,6` default `0`;
- existing rows remain complete by default.

- Existing products remain simple products; no backfill creates compositions.

- Existing sale cost values are preserved by scale-up to `14,6`.
- `inventory_transactions.type` is extended, not replaced; existing movement rows keep their types.
- Existing composition/production rows are preserved.

## 5. Rollback assessment

Rollback is **not a normal operational path** for this feature.

| Migration | Rollback risk |
|---|---|
| `000006` precision | Truncates fractional stock/ledger values to 2/4 decimals. Data-lossy. |
| `000010` sale cost | Truncates fractional cost to 2 decimals. Data-lossy. |
| `000013` enum | Removing `production` fails or truncates if production movements exist. Delete/archive those rows through an audited process first. |
| `000014` production table | Drops order metadata but leaves production ledger movements and composition runs; downstream reports would see movements without order metadata. |
| `000015` sale completeness | Drops completeness flags; incomplete sales become indistinguishable. |

Recommended rollback order if ever required:

1. stop writes and export audit evidence;
2. reverse/repair production movements through an audited process;
3. roll back 015, 014, 013;
4. preserve composition run snapshots;
5. only then consider 010/006, accepting precision loss.

No destructive rollback was executed during P8.

## 6. Database compatibility

- Project tests use MySQL (`phpunit.xml` forces `DB_CONNECTION=mysql`, database `invenos_testing`).
- Laravel supports the enum `change()` on MySQL/MariaDB; the production target is MySQL/MariaDB.
- `.env.example` defaults to SQLite, but the application/testing deployment in this repository is MySQL. SQLite is not treated as proof of production compatibility.
- No PostgreSQL/SQL Server-specific SQL was added.
- `DB::raw` report expressions use MySQL-compatible functions (`COALESCE`, `GREATEST`, `CASE`, `CAST`). These are existing deployment assumptions.

## 7. Deployment requirements

### Application

- PHP version compatible with the existing Laravel application;
- MySQL/MariaDB with foreign-key and enum support;
- `pdo_mysql`;
- writable `storage/` and `bootstrap/cache/`;
- `APP_KEY`;
- configured database credentials;
- queue driver if background jobs are used (`QUEUE_CONNECTION` is `database` by default);
- `mysqldump` available for the backup module.

### Release commands

```text
composer install --no-dev --optimize-autoloader
php artisan migrate --force
npm ci
npm run build
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

Run the queue worker and scheduler according to the existing deployment:

```text
php artisan queue:work
php artisan schedule:work    # or system cron: * * * * * php artisan schedule:run
```

The scheduler currently runs `backup:run --scheduled` every minute with `withoutOverlapping(180)`. This is pre-existing and should be reviewed operationally; P8 does not change it.

### Build artifacts

`npm run build` rewrites tracked `public/build`. P8 restored the tracked artifacts after verification. **Rebuild before deployment**; do not deploy the old manifest without rebuilding.

### Post-deploy checks

```text
php artisan migrate:status
php artisan route:list --path=production
php artisan route:list --path=composition
php artisan stock:reconcile
```

Verify production/manufacturing pages load after the build, and confirm backup/restore includes:
`product_compositions`, `product_composition_items`, `composition_runs`, `composition_run_items`, `return_component_recoveries`, `production_orders`.

`config/backup.php` excludes only cache/session/job/backups/restore tables, so composition/production tables are included by default.

## 8. Known deployment limitations

- No zero-downtime migration strategy; schema changes should be applied in a maintenance window if traffic is active.
- Precision rollback truncates data.
- Production enum rollback requires data cleanup.
- No feature flag for composition/manufacturing; route/controller deployment is the switch.
- No separate queue jobs or scheduled production work; all execution is synchronous inside HTTP/service transactions.
- Single-location stock model; no warehouse/location table.
- 9 pre-existing Auth/Profile test failures remain and are unrelated to deployment of composition.

The migrations are additive and MySQL-compatible, fresh-install and upgrade paths were exercised, and the new P8 migration applied cleanly. Deployment is possible with the documented precision/rollback constraints and the pre-existing build-artifact workflow.
