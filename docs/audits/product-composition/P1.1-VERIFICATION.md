## 3. Versioning verification

Verified in `CompositionService`:

- first save creates version 1 and is active;
- every save creates `max(version)+1`;
- previous active version is deactivated, not deleted;
- historical versions and their items remain queryable;
- active lookup orders by version descending;
- `update()` delegates to versioned `save()`;
- parent product row is locked inside the transaction;
- validation happens before writes;
- failed validation leaves the active version intact;
- unique `(product_id, kind, version)` is the final concurrency guard.

The historical-run test creates a `composition_runs` row pointing at v1, saves v2, deactivates v2,
and confirms the run and v1 still exist.

**Verdict:** version history is preserved; a version is never rewritten in place.

## 4. Cycle and nesting verification

Verified:

- direct self-reference;
- A → B → A;
- A → B → C → A;
- cycle across `assembly` and `consumption` kinds;
- inactive nested composition edges are ignored;
- valid acyclic nesting is allowed;
- depth beyond 20 is rejected;
- editing an existing active composition is validated against the active graph with the old
  composition excluded.

**Verdict:** cycle detection cannot be bypassed by editing an active composition.

## 5. Unit verification

Findings:

- P1 stores `quantity_base` as authoritative.
- `display_unit_id` is validated for known and compatible measurement type.
- The existing `ProductUnitService` had no public conversion method; its conversion factor was
  private.

Correction:

- Added `ProductUnitService::convert(float $value, string $from, string $to): ?float`.
- Normalized unit ids to lowercase/trimmed input.
- Reuses the existing factor table; no second conversion engine.
- Verified: `g→kg`, `kg→g`, `g→mg`, `ml→liter`, uppercase `KG→G`, incompatible dimensions return
  null, unknown units return null.

**P2 responsibility:** convert display quantity to base quantity server-side from the submitted
`quantity` + `unit_id`; never trust a client-supplied base quantity or cost.

## 6. Product lifecycle verification

- Product soft delete is blocked by composition ownership or component usage.
- Force delete of a component with composition history is blocked by the FK.
- Deleting a composition with runs is blocked by the FK.
- Deleting a run cascades its run items.
- Deactivation does not delete composition history.

Correction:

- `ProductPolicy::canPermanentDelete()` was a no-op. It now calls `deleteBlocker()` and blocks
  permanent deletion when transaction or composition history exists.

**Verdict:** composition and run history are protected.

## 7. Authorization and tenancy

- `ProductCompositionPolicy` is registered with `Gate::policy()`.
- Admin can view/manage; salesman can view only; inactive users are denied.
- Permissions `products.composition.view` and `products.composition.manage` are seeded.
- Branch is single-tenant; no company columns were added.
- P1 has no HTTP boundary; P2 must call the policy at every composition endpoint.

No authorization bypass was found in the domain services, because P1 services do not perform HTTP
authorization. P2 adds that enforcement.

## 8. Inventory isolation

Verified by `CompositionServiceTest` and `CompositionSchemaTest`:

- create, update/version, and deactivate leave stock unchanged;
- no `inventory_transactions` rows are created;
- no `consumption` movements are created;
- no `composition_runs` are created by template management.
