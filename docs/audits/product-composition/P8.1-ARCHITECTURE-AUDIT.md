## 2. Architecture summary

### Template layer

- `product_compositions` and `product_composition_items` are versioned, immutable-in-history templates.
- `CompositionService` creates a new version instead of mutating the active formula.
- `CompositionValidator` rejects self-reference, duplicates, invalid/archived/non-inventory components, incompatible units, cycles and depth over 20.
- Template management is inventory-neutral.

### Execution layer

- `CompositionExecutionService` is the single execution engine.
- `execute()` owns its transaction for manual use.
- `executeWithinTransaction()` is the caller-owned variant used by `SaleService` and `ProductionService`.
- The engine expands nested consumption compositions, converts to base units, scales output, applies wastage and overrides, aggregates repeated components, locks products in ascending id order, preflights stock, writes canonical `consumption` movements, and stores an immutable run/run-item snapshot.
- Idempotency is database-backed by `composition_runs.idempotency_key`.

### Commercial layer

- `SaleService` creates one commercial sale line per POS line.
- Consumption products do not deduct their own stock; components are consumed.
- Assembly/simple products keep existing parent-stock sale behavior.
- `sale_items.cost_price` is the unit cost per base unit.
- P5's `CogsCalculator` is the canonical COGS path; composition cost is read from immutable run items.

### Returns layer

- `ReturnService` remains the only return document lifecycle.
- Commercial refund, credit note and material restoration are separate facts.
- Restoration is explicit, proportional, cumulative and idempotent through `return_component_recoveries`.
- Reversal uses compensating ledger movements; component runs remain immutable.

### Manufacturing layer

- `ProductionService` owns draft → in-progress → completed → reversed and cancellation.
- Execution calls the P3 engine with `requiredKind = assembly`.
- Components are consumed through P3; finished goods are received through `inventory_transactions.type = production`.
- Production cost is the P3 component snapshot total; complete unit cost is transferred into finished-goods weighted average.
- Incomplete cost is quarantined in `uncosted_qty`, never fabricated as zero.
- Reversal is explicit, quantity-checked, idempotent and does not restore components.

## 3. Findings

### Critical

No unresolved critical finding on the source branch.

### High

| # | Finding | Status | Correction / evidence |
|---|---|---|---|
| H1 | **Uncosted finished stock was silently valued on sale.** `SaleService` decremented `uncosted_qty` but still wrote the previous/average `cost_price`, and simple COGS had no completeness flag. Incomplete production could therefore produce complete-looking profit. | **Resolved** | Added `sale_items.cost_complete` and `sale_items.uncosted_quantity` via migration `2026_11_15_000015`; `SaleService` now stores known cost per base unit plus an explicit incomplete flag; `CogsCalculator` aggregates simple uncosted lines; report payloads/UI expose the flag. Tests: `test_sale_of_incomplete_finished_stock_is_flagged_and_not_fabricated`, `test_mixed_costed_and_uncosted_sale_keeps_known_cost_but_flags_incomplete`. |
| H2 | **Production reversal did not re-base weighted-average cost.** The reversing `production` movement removed stock at the original cost, but `average_cost` stayed unchanged. If later receipts had changed the average, remaining stock was misvalued. | **Resolved** | `ProductionService::applyFinishedGoodsReversalCost()` removes the original cost from book value and recalculates the remaining costed quantity. It also refreshes the locked product after the ledger movement so stale model state cannot overwrite the new stock balance. Test: `test_reversal_rebases_weighted_average_to_remaining_stock_cost`. |
| H3 | **Fashion company stock is not hydrated by composition execution.** On `variation/clothing-erp`, `CompanyStockService` is authoritative; P3 preflight reads `products.stock_quantity`. Porting P3 unchanged could preflight against another company's mirror. | **Blocked** | Target-only integration risk. Must hydrate/lock the active company's `company_product_stock` before preflight and cost resolution. Documented in `P8.6-FASHION-COMPATIBILITY.md` and `P8.7-FASHION-INTEGRATION-PLAN.md`. |
| H4 | **Fashion idempotency indexes are global.** Source migrations add global unique `sales.idempotency_key`, `returns.idempotency_key`, `composition_runs.idempotency_key`, `production_orders.idempotency_key`. Fashion scopes uniqueness by company. | **Blocked** | Target-only migration change: replace with company-scoped unique indexes after adding company ownership. |

### Medium

| # | Finding | Status | Assessment |
|---|---|---|---|
| M1 | Nested composition versions are not locked/revalidated after explosion. The top-level composition version is rechecked under lock; a nested active version could change between explosion and movement. | Open | Narrow concurrency window. The top-level lock prevents the most common edit race. A future hardening pass should lock nested composition rows in id order and verify versions. Documented as a limitation; no code change to avoid introducing a new lock-order/deadlock path without a concurrency test. |

| M3 | Production usage/history summaries treat reversed orders as gross output/cost. Component consumption should remain because reversal never restores components, but output/cost need a gross-vs-reversed presentation. | Open | Rows carry `status = reversed`; no silent deletion of history. A future report improvement should add explicit completed/reversed/net output fields. |
| M4 | Weighted-average production cost logic duplicates the existing purchase-receipt formula in `PurchaseService`. | Open | Same convention, separate code. A shared cost service would reduce drift but is a broader refactor. Tests cover both paths. |

## 4. Dead code and duplicate paths

- **No second execution engine.** P4 and P7 both call `CompositionExecutionService`; no manufacturing-specific consumption implementation exists.
- **No duplicate stock mutation path.** Component consumption, production receipt, return restoration and sale movement all go through `InventoryService`.
- **No duplicate COGS engine.** P&L, bill-wise profit, overview, day book and balance sheet use `CogsCalculator`.
- **No legacy transaction engine.** `app/Domains/Transactions/Services/TransactionEngine.php` and `TransactionServiceProvider` are deleted.
- **Template management is isolated.** Composition CRUD never calls the inventory ledger.
- **Production does not create revenue.** No sale, payment, receivable/payable or invoice row is created by manufacturing.

The duplicate weighted-average formula (M4) is a code-level duplication, not a competing stock or ledger path.

## 5. Transaction and idempotency review

| Operation | Boundary | Idempotency |
|---|---|---|
| Composition save/version | Service transaction + product lock | Unique `(product, kind, version)` |
| Manual composition execution | Service-owned transaction | Unique run key; pending run claims key before preflight |
| Sale + composition | `SaleService` outer transaction, caller-owned execution | `sales.idempotency_key`; per-line composition key |
| Return create | Service transaction | `returns.idempotency_key` |
| Return complete | Locked return transaction | Status/effects guard + unique recovery rows |
| Production create/update/start/cancel | Service transaction + order lock | No stock effect |
| Production execute | Service transaction + order/product locks, P3 inside caller transaction | `production_orders.idempotency_key` + deterministic run key |
| Production reverse | Service transaction + order/product locks | `reversal_idempotency_key` unique |

No new transaction boundary was added in P8. The P3 caller-owned contract remains intact.

## 6. Historical integrity

- Composition runs and run items are immutable snapshots.
- Template edits create new versions; old versions remain queryable.
- Production orders and runs are not rewritten on reversal.
- Returns never mark composition runs reversed.
- Sale-item COGS compatibility snapshots are not recalculated.
- The P8 sale cost-completeness fields are written at sale time and are not recomputed from current stock.
- The P8 production reversal correction updates only the live finished-product average, not the historical production cost snapshot.

---

## 7. Performance and query review

- P3 locks products in ascending id order; repeated components are aggregated into one movement.
- Sale and production composition execution is bounded by the composition tree, not by cart size.
- Report queries are grouped; component usage aggregates in PHP.
- No unbounded component payload is returned to POS.
- Component search is paginated and server-side.
- Potential future work: nested composition row locking, SQL-level usage aggregation, and report indexes on very large production histories.

## 9. Remaining risks

1. **Fashion company-stock hydration** — highest-risk port item; blocked until approval.
2. **Fashion idempotency uniqueness** — must be company-scoped before production use.
3. **Nested composition version race** — narrow, documented, not code-fixed.
4. **Reversed production reporting** — rows are truthful but summaries are gross.
5. **Single-location stock** — no warehouse or location ledger.
6. **Incomplete-cost UI** — flagged rather than corrected; known costs remain known subtotals.
7. **Pre-existing missing Auth/Profile pages** — 9 test failures, unrelated to composition.
8. **No product variations on the actual fashion branch** — do not invent or port a variant model.

---

## 10. Verdict

The source branch architecture is coherent and does not contain a second inventory, ledger or costing engine. The two high-severity source accounting defects found in P8 were corrected and covered by regression tests.

Fashion integration is **not** authorized by this audit. It is a selective port with target-specific company-stock, company-ownership and idempotency work, and it must wait for explicit approval.
