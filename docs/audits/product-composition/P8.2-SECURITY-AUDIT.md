## 1. Authentication

All composition and production routes are inside `Route::middleware('auth')`:

- guests are redirected/denied;
- JSON composition routes return the app's unauthenticated response;
- inactive users are denied by policy/gate checks;
- no public composition or production endpoint exists.

Production and composition pages are authenticated Inertia responses.

**Result: PASS.**

## 3. Ownership and cross-company protection

### Source branch

- Single-tenant `BusinessContext`; no company/organization columns.
- `CompositionSchemaTest` asserts no `company_id`/`organization_id` on composition tables.
- Cross-company references are impossible by construction because no company dimension exists.
- This is not a claim of multi-tenant security; it is a single-tenant deployment boundary.

### Fashion target

The target branch adds organization/company ownership and company stock. Composition is **not** company-aware. Required target protections are documented in P8.6/P8.7:

- organization scope on product compositions and component products;
- company scope on runs, production orders and recoveries;
- company-scoped idempotency;
- company filters in COGS/production reports;
- company guards on sale item, return and run references.

**Source result: PASS (single-tenant). Target result: BLOCKED pending integration.**

---

## 4. Location ownership

- No location/warehouse stock table exists on either branch.
- `location` is a display/filter snapshot on runs and production orders.
- Composition preflight and movements operate on the single product stock balance.
- Production finished receipt/reversal is single-location.
- No cross-location or cross-company stock mutation is possible because no location stock model exists.

This is a documented limitation, not a location authorization control.

---

## 5. Client input trust

### Composition execution

Rejected or server-resolved:

- composition ID must belong to the route product;
- component IDs/quantities/units are resolved from the active template;
- overrides accept only a template item ID + display quantity/unit; base quantity is converted server-side;
- optional item IDs must belong to the active tree;
- costs are never accepted from the client;
- output quantity is validated and converted;
- run/sale/production IDs are not accepted as arbitrary links.

Manual execution accepts `source_type`, `source_id`, `reference` and `location` as audit metadata. This is admin-only and cannot create a sale, payment or COGS link. See P8.1 M2.

### Returns/recovery

- Recovery accepts only `composition_run_item_id` + quantity.
- The run item must belong to the sale item's completed composition runs.
- The sale item must belong to the referenced sale.
- Client-recovered quantity is clamped by server eligibility.
- Component identity/unit/cost are server snapshots.
- Refund amount remains bounded by the return value (pre-existing commercial rule).

### Production

- Client selects product/composition/planned quantity/unit/output quantity.
- Server verifies product activity, inventory tracking, composition ownership, assembly kind, version and unit compatibility.
- Component identities, component costs and finished unit costs are never accepted.
- Production order IDs are route-bound; no cross-order composition link is accepted.

**Result: PASS for composition/production. Manual source metadata and pre-existing return monetary fields remain documented trust boundaries.**

## 6. Nested record protection

- Composition routes verify `composition.product_id === product.id`.
- Composition run sales linkage is server-created; sale item ID is not a client field.
- Recovery verifies run item ownership via the sale item and completed runs.
- Production execution verifies composition version/product.
- Reports are admin-only.
- Deletion is blocked when composition/returns/production history exists.

**Result: PASS.**
