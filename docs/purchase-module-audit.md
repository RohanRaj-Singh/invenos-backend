### Critical Finding: No Purchase Unit Entity

The prototype's Pack dropdown (Unit column) expects:
1. **Default purchase config** — `product.purchaseConfig` (name, quantity, cost)
2. **Custom unit options** — generated by `purchaseStrategy.getCustomUnitOptions()`
3. **Base unit fallback** — raw stock unit

None of these are currently persisted in a structured way. The `purchaseStrategy` domain module generates options dynamically based on the product's base unit + measurement type, but the `purchaseConfig` object is derived from a normalization mapping that checks `p.purchase_units?.[0]` — which doesn't exist (no `product_purchase_units` table).

**Recommendation**: Since this is purely UI state for the purchase form's default pack selection, leave it as frontend-derived defaults. The `cost_price` column on the Product model (if added) could provide a hint for the default unit cost, and the unit could always default to the product's base unit. The UI dropdown would then show: base unit (derived from product's unit), and any custom options from `purchaseStrategy` (which calculates them from measurement type).

## Step 2 — Purchase Flow Audit

```
UI Flow                                    Backend Flow
─────────                                   ─────────────
Open Purchase Page
    ↓
PurchaseController::create()
    ↓
Inertia renders PurchaseBill.tsx
    ↓
Load products + suppliers from props
    ↓
User selects supplier (SupplierCombobox)
    ↓
User searches product (TransactionSearchBar)
    ↓
Product found → addToCart()                  Frontend-only: computes default cost
    ↓                                           from normalization (cost_price || 0)
User edits unit, qty, cost, disc%             Frontend-only: updates cart state
    ↓
User clicks "Record Purchase"
    ↓
router.post('/purchases', payload)  ─────────→ PurchaseController::store()
                                                     ↓
                                                CreatePurchaseRequest::rules()
                                                     ↓
                                                CreatePurchaseData::fromRequest()
                                                     ↓
                                                PurchaseService::create()
                                                     ↓
                                                Validate supplier role
                                                     ↓
                                                Create PurchaseBill (with discount)
                                                     ↓
                                                For each item:
                                                  → Find Product
                                                  → Create PurchaseBillItem
                                                  → Create InventoryTransaction (purchase, +)
                                                  → Increment product stock_quantity
                                                  → Recalculate product status
                                                     ↓
                                                DB::transaction → commit
                                                     ↓
                                                Return to purchase list with flash
```

**Issues identified:**

1. **`stock_quantity` updated via raw `increment()`** (line 100) instead of through `InventoryService::recordTransaction()`. This violates the domain rule that InventoryService is the sole modifier of stock.
2. **`running_balance` computed BEFORE the increment** (line 93: `$product->stock_quantity + $baseQuantity`) — correct but fragile. If the increment method changes, the running_balance becomes wrong.
3. **Supplier balance NOT updated** — making a purchase affects the supplier's `current_balance`, but the PurchaseService never calls `ContactService` to update it.
4. **`amount_paid` does not create a financial transaction** — a payment is recorded on the purchase but no `FinancialTransaction` record is created. The Payments module has no visibility of purchase payments.

## Step 11 — Risks

| Risk | Severity | Mitigation |
|---|---|---|
| **Stock desync**: PurchaseService increments stock AND creates transaction — if one fails, they desync | High | Move all stock writes through `InventoryService::recordTransaction()` inside the same DB transaction |

## Final Architecture Decisions (Answering All 7 Business Policy Questions)

### Q1: Product Cost Policy

**Decision: Two concepts — `last_purchase_cost` (auto-updated) and `default_purchase_cost` (optional, manual).**

#### Which field(s) should exist?
**Two fields on the `products` table:**

| Field | Behaviour |
|---|---|
| `last_purchase_cost` | Auto-updated after every completed purchase. Default for Purchase page prefills. |
| `default_purchase_cost` | Optional, manually maintained. For future negotiated/standard supplier pricing. Not used in MVP. |

#### Why two fields?
The business has two distinct needs:
1. **"What did we last pay?"** — a historical convenience for prefilling the next purchase form. This is `last_purchase_cost`, auto-updated on every purchase.
2. **"What should it cost?"** — a negotiated or standard supplier price that the business may want to maintain independently of purchase history. This is `default_purchase_cost`, optional and manual.

Two concepts = two fields. They serve different purposes. Having both is justified when a business maintains negotiated supplier pricing that differs from the last transactional cost.

#### For the MVP:
Only `last_purchase_cost` is required. `default_purchase_cost` column exists in the schema but is not wired into the Purchase form flow until a business requirement emerges.

#### Which value should prefill the Purchase page?
**`last_purchase_cost`**. It reflects the most recent market reality. If the price has changed, the user sees the old price and edits it to match the current invoice.

#### Should every successful purchase automatically update the Product?
**Yes, always for `last_purchase_cost`.** The `unit_cost` from each new purchase line item becomes the new `last_purchase_cost`. No exceptions. Even if the user overrides the cost on the form, that override is what gets saved as `unit_cost` and becomes the new `last_purchase_cost`.

#### Long-term implications:

| Concern | Impact |
|---|---|
| **COGS calculation** | Not affected. COGS uses actual purchase item costs (FIFO/weighted average). Product-level fields are convenience, not accounting inputs. |
| **Profit reporting** | Not affected. Profit uses actual sale prices minus actual purchase costs from PurchaseBillItems. |
| **Inventory valuation** | Not affected. Valuation uses `stock_quantity × min(selling_unit_price)` (sales-value method), not purchase costs. |
| **Price trend analysis** | `last_purchase_cost` provides a basic price history. A formal price history table can be added later if trend reporting becomes a requirement. |

### Q2: Supplier Balance Policy

**Model: Cached outstanding payable, updated by PurchaseService directly.**

#### What `current_balance` represents:
A cached projection of net outstanding payable:

```
current_balance = SUM(PurchaseBill.total_amount - PurchaseBill.amount_paid) for unpaid/partial purchases from this supplier
```

This is exactly analogous to `product.stock_quantity` — a cached value for O(1) reads, with the authoritative data living in the transaction records.

#### Should it be cached or calculated dynamically?
**Cached.** The Contacts list page displays balances for all contacts. Computing from purchase aggregates on every render would require N+1 queries across the full purchase history for every contact. Caching on the `contacts` table gives consistent fast reads.

#### Which service should own updates?
**PurchaseService directly.** Rationale:
- PurchaseService already has the DB transaction open
- PurchaseService already has the Contact loaded (`$supplier = Contact::findOrFail(...)`)
- Adding `$supplier->increment('current_balance', $outstanding)` is a one-line change inside the existing atomic transaction
- A future `PaymentService` would decrement `current_balance` when payments are recorded

#### Should a dedicated FinancialService own it?
**Not yet.** A FinancialService/SupplierLedger is a future concern. Creating one now would add abstraction without a concrete consumer. When the Payments module is built:
1. `PaymentService::recordPayment()` decrements `current_balance`
2. A reconciliation job can recompute `current_balance` from PurchaseBill data if it ever drifts
3. If an Accounting module needs ledger-level detail, it reads from PurchaseBillItems directly, not from the cached balance

---

### Q3: Financial Transactions

**Recommendation: Defer until Payments/Accounting module is implemented.**

#### Should a financial transaction be created whenever `amount_paid > 0`?
**Not yet.** The PurchaseBill already records `amount_paid` and `payment_status` — sufficient for current business needs:
- Purchase list displays payment status
- Purchase detail shows how much was paid vs outstanding
- Supplier balance (Q2 above) tracks the net payable

Creating a `FinancialTransaction` now would introduce coupling to a module (`PaymentService`, `financial_transactions` table) that has no concrete consumer yet. The data model is complete as-is.

#### Should partially paid purchases create payable records?
**Already captured.** `PurchaseBill.outstanding_balance` tracks the unpaid portion. Supplier balance aggregates this. A separate "payable record" would duplicate existing data.

#### When would this change?
When the Payments module is implemented, `PaymentService::recordPayment()` should:
1. Decrement `Contact.current_balance`
2. Create a `FinancialTransaction` record
3. Update `PurchaseBill.amount_paid` and `outstanding_balance`

At that point, `PurchaseBill.amount_paid` becomes a cached projection of the FinancialTransaction ledger, and PaymentService becomes the authoritative writer for payments.

### Q5: Backend Calculations

**Backend is the authoritative source for ALL monetary calculations. Frontend values are overridden.**

| Value | Frontend Sends | Backend Computes |
|---|---|---|
| `total_cost` (line total) | Sent but **ignored** | `purchase_quantity × purchase_pack_qty × unit_cost × (1 - discount_pct / 100)` |
| `subtotal` | Sent but **ignored** | `sum(line totals across all items)` |
| `total_amount` | Sent but **ignored** | `subtotal - discount` |
| `outstanding_balance` | Sent but **ignored** | `total_amount - amount_paid` |
| `payment_status` | Sent as hint | `'paid'` if amount_paid >= total_amount, `'partial'` if amount_paid > 0, `'unpaid'` otherwise |

**Additional calculations moved to backend:**
- `running_balance` on InventoryTransaction — always computed by InventoryService from actual stock values with `lockForUpdate()`
- Product `status` (in-stock/low-stock/out-of-stock) — computed from actual stock_quantity vs low_stock_threshold

**Why:** Protects against modified HTTP requests, stale frontend state, JavaScript calculation errors, and future pricing changes. The frontend is a presentation layer.

### Q6: Inventory Ownership

**Confirmed: InventoryService is the sole service allowed to modify inventory.**

| Operation | Allowed Service | Currently Violated? |
|---|---|---|
| Create inventory transaction | **InventoryService only** | ❌ PurchaseService calls `InventoryTransaction::create()` directly |
| Modify `product.stock_quantity` | **InventoryService only** | ❌ PurchaseService calls `$product->increment()` directly |
| Update `running_balance` | **InventoryService only** | ❌ Currently computed in PurchaseService |
| Recalculate `product.status` | **InventoryService only** | ❌ `PurchaseService::recalculateStatus()` is private — must move to InventoryService |

**Public API for InventoryService (intent-based):**

```php
class InventoryService {
    public function recordPurchase(int $productId, float $quantity, ...): InventoryTransaction;
    public function recordSale(int $productId, float $quantity, ...): InventoryTransaction;
    public function recordReturn(int $productId, float $quantity, ...): InventoryTransaction;
    public function recordAdjustment(int $productId, float $quantity, string $type, ...): InventoryTransaction;

    private function applyInventoryChange(...): InventoryTransaction; // shared internal logic
}
```

**PurchaseService orchestrates but does not touch inventory.** It calls `InventoryService::recordPurchase()` and trusts InventoryService to handle all stock mutations. This is exactly the domain rule established in the architecture.

### Q7: Transaction Safety

**All Purchase operations execute inside a single database transaction. Verified.**

Current `PurchaseService::create()` wraps in `DB::transaction()`:
- ✅ PurchaseBill creation
- ✅ PurchaseBillItem creation (loop)
- ✅ InventoryTransaction creation (loop) — will move to InventoryService::recordPurchase() but stays inside same transaction
- ✅ Product stock update — will move to InventoryService but stays inside same transaction
- ✅ Product status recalculation — will move to InventoryService but stays inside same transaction

**Will be added inside the same transaction:**
- ⚠️ `Contact.current_balance` update
- ⚠️ `Product.last_purchase_cost` update

**The system is fully atomic.** No writes occur outside the transaction. PHP process death, DB connection loss, or any exception mid-operation causes a complete rollback. No partial state can exist.

#### Concurrency safeguard:
`InventoryService::applyInventoryChange()` uses `Product::lockForUpdate()->findOrFail()` before reading stock to compute running_balance. This prevents stale reads when two purchases of the same product overlap.

## Summary of All 7 Decisions

| # | Question | Decision | Key Justification |
|---|---|---|---|
| 1 | Product Cost | **Option A — `last_purchase_cost`**, auto-updated | Retail costs fluctuate; one field is sufficient; COGS not affected |
| 2 | Supplier Balance | **Cached projection**, updated by PurchaseService | Same pattern as `stock_quantity`; no FinancialService needed yet |
| 3 | Financial Transactions | **Deferred** until Payments module | PurchaseBill already tracks amount_paid and outstanding |
| 4 | Historical Snapshots | **All purchase-specific fields immutable** | Only `base_unit_name` bug needs fixing |
| 5 | Backend Calculations | **Backend authoritative** for all monetary values | Frontend values ignored; computed server-side |
| 6 | Inventory Ownership | **InventoryService only** | PurchaseService bypasses it today — must refactor |
| 7 | Transaction Safety | **Single DB transaction** for all writes | Atomic; `lockForUpdate()` for concurrency |
