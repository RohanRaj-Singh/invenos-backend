## 1. Executive Summary

The core transactional foundation is complete: Products, Unit Relationships, Inventory Engine, Purchases, Sales, Contacts, Lifecycle Framework. The next milestone is **Returns** — completing the transaction lifecycle — followed by **Reporting** on a complete and stable data model.

**Key architectural bets (revised):**

| Bet | Rationale |
|-----|-----------|
| All transactions run through a **Transaction Engine** | Purchase, Sale, Return, Adjustment, Transfer, Manufacturing — each defines its own effects. One engine prevents module-specific service drift. |
| **Single polymorphic Return model** | One `Return` model with `type: SALE|PURCHASE`. One controller, one service, one report, one print layout. No duplication. |
| Inventory is event-driven | The engine doesn't care where movements originate. `InventoryTransaction` is the single source of truth for stock. |
| **Inventory reports consume `InventoryTransaction` only** | No joins to Sale, Purchase, or Return for stock-level reports. Sales/Purchase reports consume their respective doc types. |
| Historical documents never change | Deleting a return reverses its effects but preserves the original document. `SoftDeletes` + `RecordLifecycleService`. |
| Reports are built in two phases | Operational reports first (stock, sales, purchases, contacts). Analytical reports later (profit, dead stock, ABC analysis). |

## 3. Guiding Principles

### 3.1 Every Business Event Is an Immutable Record

```
Sale #105         → InventoryTransaction (type: sale, qty: -50)
Return #12        → InventoryTransaction (type: sale-return, qty: +10)
Purchase #203     → InventoryTransaction (type: purchase, qty: +100)
Adjustment #7     → InventoryTransaction (type: adjustment, qty: -5)
```

Reports never guess. They aggregate.

### 3.2 Transactions Are First-Class Documents

A Return is not a modification of an existing Sale or Purchase. It is a new business transaction that references an original:

```
Sale #105                Purchase #203
    │                          │
    ▼                          ▼
Return #12 (type: SALE)   Return #8 (type: PURCHASE)
```

Both the original and the return remain permanent historical records.

### 3.3 The Transaction Engine Is the Single Entry Point

> ⭐ **Revision:** Instead of separate `SaleService`, `PurchaseService`, `ReturnService`, build one `TransactionEngine` that all transaction types pass through.

Each transaction type defines:
- **Inventory effect** — which direction, which quantity
- **Financial effect** — how it moves money
- **Contact effect** — how it changes customer/supplier balance
- **Validation rules** — what constraints apply

This prevents every future module (Transfers, Manufacturing, Warehouses) from building their own service that duplicates the same patterns.


- **Completed**: Fully processed — all effects applied
- **Cancelled**: Voided before completion — no effects

## 5. ⭐ Transaction Engine (Revised)

### 5.1 Architecture

Instead of separate services for every transaction type, one `TransactionEngine` processes all:

```
┌─────────────────────────────────────────────────┐
│                TransactionEngine                  │
│                                                   │
│  process(TransactionData $data): Transaction      │
│  preview(TransactionData $data): ImpactPreview    │
│  validate(TransactionData $data): void            │
│                                                   │
│  ┌──────────────────────────────────────────┐    │
│  │         TransactionType (interface)      │    │
│  ├──────────────────────────────────────────┤    │
│  │  inventoryEffect(): InventoryMovement    │    │
│  │  financialEffect(): FinancialMovement    │    │
│  │  contactEffect(): ContactBalanceChange   │    │
│  │  validationRules(): array                │    │
│  └──────────────────────────────────────────┘    │
│         ▲          ▲          ▲          ▲       │
│         │          │          │          │       │
│  ┌──────────┐ ┌────────┐ ┌──────┐ ┌──────────┐  │
│  │  Sale    │ │Purchase│ │Return│ │Adjustment│  │
│  │  Type    │ │ Type   │ │Type  │ │ Type     │  │
│  └──────────┘ └────────┘ └──────┘ └──────────┘  │
│         ▲          ▲                             │
│         │          │                             │
│  ┌──────────┐ ┌──────────┐                       │
│  │ Transfer │ │Manufact.│                       │
│  │ (future) │ │(future)  │                       │
│  ���──────────┘ └──────────┘                       │
└─────────────────────────────────────────────────┘
```

### 5.2 TransactionType Interface

```php
interface TransactionType
{
    /** Define the inventory movement direction and quantity. */
    public function inventoryEffect(TransactionData $data): InventoryMovement;

    /** Define the financial transaction effect. */
    public function financialEffect(TransactionData $data): ?FinancialMovement;

    /** Define how the contact balance changes. */
    public function contactEffect(TransactionData $data): ?ContactBalanceChange;

    /** Business rules for this transaction type. */
    public function validationRules(): array;

    /** Human-readable label. */
    public function label(): string;
}
```

### 5.3 TransactionType Implementations

| Type | Inventory Effect | Financial Effect | Contact Effect |
|------|-----------------|------------------|----------------|
| `Sale` | `-qty` (deduct) | `+receivable` (invoice) | `+balance` (customer owes) |
| `Purchase` | `+qty` (add) | `+payable` (bill) | `+balance` (we owe supplier) |
| `SaleReturn` | `+qty` (add back) | `-receivable` (refund/credit) | `-balance` (customer owes less) |
| `PurchaseReturn` | `-qty` (deduct back) | `-payable` (credit) | `-balance` (we owe less) |
| `Adjustment` | `±qty` | — | — |
| `OpeningStock` | `+qty` | — | — |
| `Transfer` (future) | `-qty` (out) / `+qty` (in) | — | — |
| `Manufacturing` (future) | `-inputs +output` | `+value` | ��� |

### 5.4 What This Unlocks

| Today (separate services) | Tomorrow (transaction engine) |
|---------------------------|-------------------------------|
| `SaleService::create()` — handles inventory, balance, financial | `TransactionEngine::process(SaleType, $data)` |
| `PurchaseService::create()` — nearly identical code | Same engine, different type |
| `ReturnService::createReturn()` — third implementation | Same engine, different type |
| Next module: builds fourth service from scratch | Implements `TransactionType` interface only |

### 5.5 Migration Path

Migration is incremental. Existing `SaleService` and `PurchaseService` are refactored to delegate to the `TransactionEngine` internally, keeping their public API compatible. New types (Return, Transfer, Manufacturing) use the engine directly.

## 6. ⭐ Single Return Model (Revised)

### 6.1 Decision: Single Polymorphic Model

**Replaces** the previously proposed `SaleReturn` + `PurchaseReturn` split.

```php
// One model. One table. One controller. One service. One report. One print layout.
class Return extends Model
{
    use SoftDeletes;

    protected $fillable = [
        'return_number', 'type',              // SALE or PURCHASE
        'reference_type', 'reference_id',      // polymorphic → Sale or PurchaseBill
        'contact_id',
        'return_date', 'reason_id', 'reason_note',
        'status',                              // pending, completed, cancelled
        'subtotal', 'discount', 'grand_total',
        'refund_amount', 'refund_method',
        'notes', 'created_by',
        'delete_reason', 'deleted_by',
    ];

    public function reference(): MorphTo
    {
        return $this->morphTo(); // Sale or PurchaseBill
    }

    public function items(): HasMany
    {
        return $this->hasMany(ReturnItem::class);
    }

    public function contact(): BelongsTo
    {
        return $this->belongsTo(Contact::class);
    }

    public function reason(): BelongsTo
    {
        return $this->belongsTo(ReturnReason::class);
    }

    public function inventoryTransactions(): HasMany
    {
        return $this->hasMany(InventoryTransaction::class, 'reference_id')
            ->where('reference_type', 'return');
    }
}

class ReturnItem extends Model
{
    protected $fillable = [
        'return_id', 'reference_item_type', 'reference_item_id', // polymorphic → SaleItem or PurchaseBillItem
        'product_id', 'product_name',
        'selling_unit_id', 'packaging_name',
        'quantity', 'base_quantity',
        'unit_price', 'total',
        'reason_id', 'notes',
    ];

    public function return(): BelongsTo { ... }
    public function referenceItem(): MorphTo { ... } // SaleItem or PurchaseBillItem
    public function product(): BelongsTo { ... }
}
```

### 6.2 Why This Is Better

| Concern | Separate Models | Single Model |
|---------|----------------|--------------|
| Return service | Two services with duplicated logic | One `ReturnService` |
| Controller | Two controllers | One controller |
| Routes | Two route groups | One route group |
| Frontend pages | Two sets of pages (SaleReturnList + PurchaseReturnList) | One `ReturnList` with type filter |
| Recycle Bin | Two entity types | One entity type with type field |
| Reports | Two report sections | One return report, filterable by type |
| Lifecycle policy | Two policies | One `ReturnPolicy` |
| Print layout | Two print views | One print view, contextual by type |

### 6.3 The `type` Field Drives Everything

```
Return::create(['type' => 'SALE', ...])
  → inventoryEffect: sale-return (+qty)
  → contactEffect: decrement customer balance
  → financialEffect: refund/credit note

Return::create(['type' => 'PURCHASE', ...])
  → inventoryEffect: purchase-return (-qty)
  → contactEffect: decrement supplier payable
  → financialEffect: supplier credit
```

## 8. Inventory Integration

### 8.1 Movement Types

Every transaction type produces `InventoryTransaction` records through the existing `InventoryService::applyMovement()`:

| Transaction Type | Recorded Type | Direction | Engine Route |
|------------------|---------------|-----------|-------------|
| Purchase | `purchase` | `+quantity` | `TransactionEngine` → `recordPurchase()` |
| Sale | `sale` | `-quantity` | `TransactionEngine` → `recordSale()` |
| **Sale Return** | **`sale-return`** | **`+quantity`** | **`TransactionEngine` → `recordReturn()`** |
| **Purchase Return** | **`purchase-return`** | **`-quantity`** | **`TransactionEngine` → `recordReturn()`** |
| Adjustment (+/-) | `adjustment` | `±quantity` | `TransactionEngine` → `recordAdjustment()` |

### 8.2 Unit Conversion

Returns always use the **same selling unit** as the original sale/purchase. The `base_quantity` field on the sale/purchase item stores the base-unit equivalent:

```
Original Sale: 2 Strips �� 10 tablets = 20 base units (deducted)
Return:        1 Strip  × 10 tablets = 10 base units (added back)
```

### 8.3 Future Compatibility

| Concern | Status | How |
|---------|--------|-----|
| FIFO costing | ✅ Compatible | Cost price stored per sale item |
| Average cost | ✅ Compatible | Can re-average on return |
| Batch tracking | ✅ Neutral | `reference_type`/`reference_id` pattern extends |
| Expiry tracking | ✅ Neutral | Same extension point |
| Multi-location | ✅ Neutral | Add `warehouse_id` to `InventoryTransaction` |

## 11. Reporting Philosophy

### 11.1 Immutable Events, Projected Views

> Every business event generates immutable records. Reports are generated by aggregating these records rather than recalculating business logic.

```
InventoryTransaction ──→ Stock Ledger, Stock Valuation, Product Timeline
Sale + Return         ──→ Sales Register, Customer Sales, Net Sales
Purchase + Return     ──��� Purchase Register, Supplier Purchases, Net Purchases
FinancialTransaction  ��─→ Day Book, Cash Flow, Payment History
AuditLog              ──→ Activity Feed, Change History
```

### 11.2 ⭐ Reports Consume the Right Source of Truth (Revised)

**Inventory reports** consume `InventoryTransaction` only — no joins to Sale, Purchase, or Return tables:

```
Stock Ledger
    ↓
InventoryTransaction (type = 'purchase' | 'sale' | 'sale-return' | 'purchase-return' | 'adjustment')
    ↓
No joins needed. One table. One query.
```

**Sales reports** consume `Sale` + `Return` (where `type = 'SALE'`):

```
Sales Register
    ↓
Sale LEFT JOIN Return ON Return.reference_id = Sale.id AND Return.reference_type = 'sale'
    ↓
Net = SUM(Sale.grand_total) - SUM(Return.grand_total)
```

**Purchase reports** consume `PurchaseBill` + `Return` (where `type = 'PURCHASE'`):

```
Purchase Register
    ↓
PurchaseBill LEFT JOIN Return ON Return.reference_id = PurchaseBill.id AND Return.reference_type = 'purchase'
```

This separation is intentional and correct:
- `InventoryTransaction` is the canonical inventory history — querying it directly is both simpler and more correct than joining through Sale/Purchase.
- Sales and Purchase reports need document-level details (invoice numbers, customer names, line items) that `InventoryTransaction` doesn't store.

## 12. ⭐ Reports: Two-Phased Roadmap

| Report | Data Source | Complexity |

| Stock Valuation | Products × unit cost | 🟢 Low |

| Sales Register | `Sale` + `Return(type=SALE)` | ��� Low |

| Product Sales | `SaleItem` grouped by product | 🟡 Medium |

### 19.3 Lifecycle Policies

```php
// Single ReturnPolicy — handles both SALE and PURCHASE types
class ReturnPolicy implements Deletable, Restorable, PermanentDeletable
{
    public function executeDelete(Model $record, User $user): void
    {
        // Reverse the inventory effect (opposite of what the return did)
        foreach ($record->items as $item) {
            $direction = $record->type === 'SALE' ? -1 : 1;
            app(InventoryService::class)->recordAdjustment(
                productId: $item->product_id,
                quantity: $direction * $item->base_quantity,
                reference: 'REV-' . $record->return_number,
                notes: "Reversal of deleted {$record->type} return",
                user: $user->name ?? 'System',
            );
        }
        // Reverse contact balance
        if ($record->contact) {
            $record->type === 'SALE'
                ? $record->contact->increment('current_balance', $record->grand_total)
                : $record->contact->decrement('current_balance', $record->grand_total);
        }
    }
}
```

Register once:
```php
$lifecycle->register(Return::class, ReturnPolicy::class);
```

### 21.3 Edge Cases

| Edge Case | Expected |
|-----------|----------|
| Return after stock adjustment | Return increases stock normally |
| Return of deleted product | Allowed — product_name preserved on item |
| Contact deleted | Return still viewable (FK SET NULL) |
| Sale deleted | Return not allowed (FK validation blocks) |
| Concurrent return creation | Row-level lock prevents double-reversal |
| Cross-unit return (strip → piece) | `base_quantity` provides consistent reversal |
| Discount on multi-item return | Proportionally applied per line |
| Multiple partial returns > 100% | Blocked by validation |
| Negative inventory from return deletion | InventoryService protects against this |

## 22. Risks & Edge Cases

| Risk | Impact | Mitigation |
|------|--------|------------|
| Return qty exceeds remaining | Data integrity error | Validation queries SUM of previous returns |
| Concurrent return creation | Double-reversal | Row-level lock on original document |
| Delete after stock adjustment | Stock goes negative | InventoryService negative stock protection |
| Returns on deleted sale | 404 error | Validation checks Document exists and not trashed |
| Discounts on partial returns | Proportional math errors | Discount ratio per line, test extensively |
| Cross-unit returns | Unit mismatch | All returns use original item's selling unit |
| Large report datasets | Slow queries | Pagination, date-range indexes |
| Report calculation drift | Silent errors | Audit log as cross-check, periodic reconciliation |
